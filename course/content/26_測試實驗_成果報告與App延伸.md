# 第 26 章｜測試實驗、成果報告與 App 延伸

程式可以跑，不代表專題完成。最後要回答：**在哪些條件下可靠？哪些條件會失敗？加入前處理到底有沒有幫助？**

這一章把工程成果整理成真正可以展示的自主學習專題。

## 學習目標

- 設計可比較的測試條件。
- 建立辨識結果紀錄表。
- 分辨功能錯誤與模型辨識限制。
- 整理專題報告架構。
- 規劃 FastAPI + Flutter 的 App 延伸。

## 一、不要只測一張成功圖片

至少準備：

```text
A 清晰掃描
B 正常手機拍攝
C 輕微傾斜
D 光線不均
E 低亮度
F 背景複雜
G 有手寫註記
```

不是每一類都保證 OMR 支援良好；測試目的就是找邊界。

---

## 二、一次只改一個主要條件

如果同時：

```text
換圖片
換 threshold
換 CLAHE
換 OMR 參數
```

最後就不知道是什麼造成差異。

例如比較前處理：

```text
同一張照片
A：直接 OMR
B：preprocess 後 OMR
```

其他條件保持一致。

如果能取得可信 ground truth，還可以計算更正式的準確率；如果不能，就誠實採用人工錯誤統計與案例分析。

## 四、錯誤分類

不要只寫：「辨識錯了。」

可以分類：

```text
音高錯誤
升降記號錯誤
漏音
多辨識
小節結構錯誤
休止符錯誤
版面失敗
OMR 完全失敗
```

這能讓「未來改善方向」更具體。

## 六、什麼是自己的貢獻？

即使 OMR 使用開源工具，學生仍然完成：

```text
圖片前處理策略
第三方 OMR 介接
MusicXML 解析
音符資料模型
三種轉換規則
標註寫回
Pipeline
輸出管理
錯誤處理
CLI
API
Web UI
測試與實驗
```

報告中應清楚區分：

```text
第三方工具負責什麼
vs
自己開發與整合什麼
```

## 七、App 延伸架構

當 Web 版本穩定後，Flutter 不需要重寫 OMR。

```text
Flutter App
↓ HTTP
FastAPI
↓
原本的 process_file()
↓
結果
↓ HTTP
Flutter 顯示
```

也就是說：

```text
核心 Python 系統不變
前端從瀏覽器多一個手機 App
```

這正是前面把核心與 Web 分開的好處。

## 八、可以延伸的方向

### 功能

- 首調唱名。
- 使用者自訂標註。
- 多聲部處理。
- 批次樂譜。
- PDF 輸入／輸出。
- 直接輸出圖片。

### OMR

- 更換其他 OMR backend。
- 比較不同辨識工具。
- 建立自己的測試集。
- 針對手機照片增加透視校正。

### 產品

- Flutter App。
- 使用者歷史紀錄。
- 雲端儲存。
- 帳號系統。
- 多裝置同步。

## 最後總結

整份課程真正學到的不是：

```text
「會用 oemer」
```

而是：

```text
問題拆解
↓
理解資料
↓
學習必要技術
↓
完成小功能
↓
驗證
↓
模組化
↓
整合
↓
介面化
↓
測試與改善
```

這才是這份自主學習專題最重要的價值。
